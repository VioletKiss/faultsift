# FS-009: Line Access Benchmark Baseline

- Status: Completed — 2026-09-01
- Owner: Unassigned
- Related ADRs: ADR-0003, ADR-0004
- Roadmap stage: M2 — Line Access / Index

## Goal

Establish a reproducible performance and memory baseline for completed physical-line streaming, adaptive index build, ready lookup, cancellation, and huge-line behavior without re-benchmarking File Access or approving resource defaults and regression thresholds.

## Context

FS-006 through FS-008 complete the M2 Line Access contract. [ADR-0004](../adr/0004-physical-line-access-and-adaptive-sparse-index.md) deliberately requires explicit checkpoint and scan resources until evidence exists. The existing [File Access baseline](../benchmarks/file-access.md) establishes lower-layer access behavior but explicitly does not measure newline scanning, line indexing, lookup, or huge-line processing.

## In Scope

- add a stable-compatible benchmark harness dedicated to `faultsift-line-access` with deterministic, streamed, bounded fixture generation and fixed random seeds;
- benchmark complete index-build throughput for representative LF/CRLF physical-line distributions and average physical footprints around 80, 200, and 500 bytes;
- measure exact logical checkpoint payload/capacity, checkpoint count, final stride, and compaction count for each build workload;
- compare explicit checkpoint-budget candidates including 16, 32, and 64 MiB without turning them into defaults;
- compare explicit scan-chunk candidates including 64 KiB and 1 MiB, plus only other bounded candidates justified by recorded methodology;
- benchmark seeded random `line()` and `line_range()` lookup latency with p50/p95 and other stable harness statistics, while reporting scanned-line and scanned-byte work where practical;
- benchmark sequential content-bearing cursor throughput with deterministic byte consumption/checksums;
- measure chunk-boundary cancellation callback frequency and observed cancellation responsiveness;
- exercise newline-dense compaction and huge-line/many-chunk behavior separately from representative log distributions;
- distinguish the actual File Access backend through diagnostics and separate Windows mapped, Windows forced-buffered when safely established by benchmark support, and Linux buffered results;
- record process RSS/VAS observations when available while clearly separating them from logical checkpoint and scan-buffer bounds;
- record environment, toolchain, fixture construction, cache limitations, commands, workloads, backend diagnostics, results, and interpretation limits in `docs/benchmarks/line-access.md`;
- compile the benchmark harness in required Windows and Ubuntu CI paths without running noisy performance measurements or enforcing timing thresholds;
- use benchmark-only dependencies only when focused and keep them out of normal runtime dependency paths.

## Out of Scope

- rerunning, replacing, or changing the FS-005 File Access benchmark baseline;
- implementing or approving `DEFAULT_CHECKPOINT_BUDGET_BYTES`, `DEFAULT_SCAN_CHUNK_BYTES`, `Default` for Line Access options, a product SLA, or a CI timing gate;
- changing scanner, cursor, checkpoint, compaction, lookup, cancellation, snapshot, or error semantics merely to improve benchmark numbers;
- adding parallel scanning, async I/O, prefetching, caching, compression, hierarchical indexes, offset reverse lookup, progressive indexing, or persistence;
- cold-cache claims without controlled platform-specific preparation;
- committing GB-scale generated fixtures or benchmark result binaries;
- Parser, Java events, Search semantics, Pattern, Timeline, Tauri IPC, UI, CLI commands, or AI benchmarks.

## Technical Constraints

- Fixtures must be generated by streaming or proven sparse techniques and protected by hard size limits. No setup path may construct a complete large fixture or huge line in memory.
- Workload names must include enough configuration to prevent results for different fixture sizes, line distributions, checkpoint budgets, scan chunks, cache conditions, backends, or harness versions from being compared as identical.
- Use fixed seeds and pre-generated lookup sequences. Repeat generation in tests and require exact equality.
- Benchmark code must consume deterministic bytes/results so scanning and lookup work cannot be optimized away.
- Report actual backend diagnostics. A Windows mapped comparison is invalid if automatic access fell back to buffered; benchmark support may establish buffered access safely but must not add a production force-backend option.
- File Access mapped `RangeView` logical exposure throughput must not be described as newline-scanning throughput. Line benchmarks must touch the bytes required by the line operation.
- Checkpoint payload/capacity, final stride, compaction count, and scan-buffer configuration are primary bounded-memory evidence. RSS/VAS and allocator observations are supplementary and may not be inferred when unavailable.
- Warm-cache runs must be labelled warm/uncontrolled. Do not claim cold-cache behavior without external controlled preparation.
- Huge-line and newline-dense cases must be reported separately from representative log throughput so pathological fixtures do not misrepresent ordinary workloads.
- Benchmark concurrency and live cursor/lookup buffers must remain at explicit bounded levels. Do not retain views, descriptors, spans, or buffers between iterations unintentionally.
- Full Criterion or equivalent performance runs are manual/local. CI compiles the harness and runs bounded correctness smoke tests only.
- Candidate measurements can support a later recommendation, but this task may not implement or declare a named resource default without a separate approved decision.
- Benchmark code remains safe Rust. A benchmark-only dev-dependency does not authorize a new normal runtime dependency.

## Acceptance Criteria

- [x] One documented stable-compatible command runs a deterministic Line Access benchmark harness without checked-in large fixtures.
- [x] Build workloads cover LF and CRLF distributions near 80, 200, and 500 average physical bytes with explicit fixture, budget, scan-chunk, backend, and cache metadata.
- [x] Results report index build throughput together with exact checkpoint payload/capacity, checkpoint count, final stride, and compaction count.
- [x] Explicit 16/32/64 MiB checkpoint-budget and 64 KiB/1 MiB scan-chunk candidates are measured or any environment-driven reduction is clearly recorded without becoming a default.
- [x] Seeded random line and line-range lookup reports latency plus scanned work where available and verifies exact results.
- [x] Sequential content-bearing cursor measurements consume deterministic content bytes and report actual processed bytes rather than descriptor counts alone.
- [x] Cancellation measurements verify callback count scales with chunks rather than physical lines and record the bounded-chunk responsiveness limitation.
- [x] Newline-dense and huge-line workloads demonstrate bounded checkpoint/buffer behavior and are labelled separately from representative throughput.
- [x] Windows results verify actual mapped/forced-buffered diagnostics when both are available; Linux results use and report the buffered backend.
- [x] The baseline document records environment, commands, fixtures, seeds, options, backend, cache limitations, results, memory methodology, and interpretation limits.
- [x] Required Windows and Ubuntu CI compile the harness and run bounded correctness tests without enforcing noisy performance thresholds.
- [x] Criterion or any equivalent harness dependency is benchmark-only and absent from the crate's normal dependency path.
- [x] No resource default, absolute threshold, semantic optimization, later index feature, Parser, Search, persistence, Tauri, UI, or AI behavior is introduced.

## Test Cases

- Generate each representative line distribution twice and verify exact fixture bytes, line count, and deterministic seed metadata.
- Generate seeded random line and range requests twice and require identical sequences; a different seed must change the sequence.
- Run bounded smoke builds for each representative distribution and verify exact line count, backend diagnostics, final stride, checkpoint count, and consumed byte totals before timing is interpreted.
- Use a small newline-dense fixture and constrained checkpoint budget to force deterministic repeated compaction; verify reported compaction and final-stride metadata.
- Run cursor and ready-lookup workloads against the same fixture and verify checksums/descriptors/spans match expected results.
- Request cancellation at a fixed callback count and verify callback frequency, bytes scanned, no returned index, and unchanged snapshot lifecycle.
- Stream a line many scan chunks long and verify benchmark setup and measured operation never retain the complete line.
- On eligible Windows storage, establish and verify mapped automatic and safely forced-buffered cases; abort or label unavailable rather than misreporting identical backends.
- On Linux, verify only buffered diagnostics and compile/run bounded smoke behavior without Windows benchmark support.
- Hold exactly the configured bounded concurrency level and verify buffers or cursor states are released between samples.
- Verify hard fixture/workload override limits reject accidental unbounded environment values.

## Risks

- OS page cache, antivirus, filesystem compression, storage hardware, and background load can dominate results.
- A benchmark that reports configured instead of actual backend selection can compare buffered access with itself.
- Fixture generation can accidentally dominate measured work or allocate a complete huge line.
- Descriptor-only consumption can make cursor throughput look unrealistically high unless content bytes are consumed.
- RSS/VAS can be misread as exact checkpoint allocation or physical-disk throughput.
- Candidate values can be silently promoted to defaults if result documentation does not preserve the decision boundary.
